# ADS 아델슨 관리자 앱 전체 구조·기능 명세

> 기준 시점: 2026-07-30  
> 대상: `admin_app/` Flutter 관리자 앱과 앱이 사용하는 Next.js 관리자 API  
> 목적: 이 문서만 읽은 다른 AI가 현재 앱의 화면 구조, 권한, 문의·고객 처리 흐름, 데이터 관계와 수정 위치를 바로 이해할 수 있도록 한다.

## 0. 한 문장으로 보는 앱

웹사이트에서 접수된 문의를 **최고 관리자 또는 보조 관리자가 담당자에게 배정하고**, 일반 관리자는 **본인에게 배정된 문의와 연결 고객만 처리**하며, 최고 관리자는 고객 중복 검토·병합·복구·관리자 관리·처리 로그까지 수행하고, 최고 관리자와 보조 관리자는 공개 웹사이트의 이미지·영상·PDF와 기본정보를 관리하는 Flutter 앱이다.

### 2026-07-30 UX 개편 우선 규칙

아래 항목은 이 문서 뒤쪽에 남아 있는 이전 화면 설명보다 우선한다.

- 앱 버전은 `1.0.20+46`이다.
- 본문은 17px, 앱바 제목은 22px, 주요 버튼 높이는 52px을 기본으로 하며 100·130·150% 시스템 글자 크기에서도 글자를 억지로 줄이지 않는다.
- 로그인 후 최초 한 번 `문의 확인 → 담당자 배정 → 기록과 완료` 3장 사용법을 표시하며, 이후에는 `설정 > 사용법 다시 보기`에서 다시 볼 수 있다.
- 문의 홈 상단에는 `배정 전`, `1일 미처리`, `3일 미처리`, `내 진행 중` 업무 요약을 표시한다.
- 문의 우선순위는 `3일 미처리 → 1일 미처리 → 배정 전 → 일반 진행 → 완료` 순이다. 기준 시각은 접수 시간이 아니라 서버의 `Inquiry.lastActionAt`이다.
- 문의 목록은 검색·범위·상태 조건을 문장으로 보여 주고 한 번에 초기화할 수 있다. 목록을 유지한 재로딩, 오류별 다시 시도, 빈 결과 안내를 제공한다.
- 여러 문의를 눈에 보이는 체크박스로 선택하고 `선택 N건`을 확인한 뒤 전용 담당자 선택 화면에서 일괄 배정할 수 있다.
- 담당자 배정은 드롭다운 즉시 변경이 아니라 전용 화면에서 담당자의 진행 건수와 3일 미처리 건수를 확인하고 최종 확인 후 저장한다.
- 문의 상세 하단 고정 동작은 `전화`, `상담 기록`, `처리 완료/다시 진행`이다. 완료 직후 10초 동안 되돌릴 수 있다.
- 상담 기록은 통화 완료·자료 발송·견적 검토·답변 대기·연락 안 됨·기타 중 하나와 선택 메모로 저장한다. 저장하지 않고 나가면 확인한다.
- 첨부파일은 파일 정보 화면을 거쳐 이미지와 PDF를 앱 안에서 미리 보고, 다운로드 진행률·취소·재시도·다운로드 후 열기를 제공한다.
- 중복 후보의 상세 대조, 최종 합치기·기존 고객 연결·새 고객 유지·복구는 최고 관리자만 수행한다. 다른 관리자는 중복 감지 여부만 보고 `검토 요청`을 보낼 수 있다.
- 고객 또는 회사가 없는 경우에도 회사 연결·새 회사 추가가 가능하다. 연결 변경·해제는 최고/보조 관리자가 수행하고 변경 전후 회사, 처리 관리자, 시각을 기록한다.
- 고객·회사 메모는 모두가 보는 공유 메모와 작성 관리자만 보는 개인 메모로 분리한다.
- 햄버거 메뉴는 권한에 따라 `관리자`, `홈페이지`, `처리 기록`, `설정`, `로그아웃`만 표시한다.

## 1. 전체 시스템에서 앱의 위치

```text
고객
└─ 공개 웹사이트 문의폼
   ├─ 문의(Inquiry) 생성
   ├─ 고객(Customer) 자동 생성
   ├─ 회사명이 있으면 회사(Company) 연결
   ├─ 첨부파일을 Supabase Storage에 저장
   ├─ 기존 고객 후보 자동 탐색
   └─ 최고 관리자에게 신규 문의 푸시 알림

Flutter 관리자 앱
├─ 로그인/JWT 보관
├─ 문의 목록·상세·배정·완료
├─ 고객 목록·상세·회사·메모·즐겨찾기
├─ 중복 고객 검토·병합·복구
├─ 관리자 계정·보조 관리자 관리
├─ 문의 처리/배정 로그
└─ 공개 웹사이트 CMS 관리
   ├─ Next.js 관리자 API
   ├─ Prisma
   ├─ Supabase PostgreSQL
   └─ Supabase Storage
```

관리자 앱은 웹 문의를 직접 생성하는 앱이 아니다. 문의와 고객은 공개 웹사이트 문의폼 제출 시 자동 생성되며, 앱은 접수 이후의 배정·처리·고객관리·웹사이트 관리를 담당한다.

## 3. 앱 시작과 전역 상태

### 시작 순서

1. `main.dart`에서 Flutter 바인딩을 초기화한다.
2. Firebase를 초기화한다.
3. 백그라운드 FCM 메시지 핸들러를 등록한다.
4. `AdsInquiryAdminApp`을 실행한다.
5. `app.dart`가 아래 서비스 인스턴스를 한 번 생성하여 각 화면에 전달한다.
   - `ApiClient`
   - `AuthService`
   - `InquiryService`
   - `CustomerService`
   - `WebsiteContentService`
   - `AdminManagementService`
   - `PushNotificationService`
6. 보안 저장소의 JWT를 읽는다.
7. 토큰이 있으면 `/api/admin/me`로 현재 관리자를 다시 확인한다.
8. 유효하면 홈을, 무효하거나 만료되었으면 로그인 화면을 표시한다.
9. 로그인 상태가 확정되면 FCM 권한과 기기 토큰을 등록한다.

### 로그인 후 최상위 화면

로그인 후 홈은 두 화면을 유지하는 `IndexedStack`이다.

```text
홈
├─ 0: 문의 관리  ← 항상 기본값
└─ 1: 고객 관리
```

- 로그인 직후 기본 화면은 `문의 관리`다.
- 문의 관리와 고객 관리는 하단 내비게이션으로 전환한다.
- 두 화면은 `IndexedStack`에 유지되므로 탭을 바꿔도 기존 화면 상태가 보존된다.
- 로그아웃 후 다시 로그인하면 홈 인덱스가 문의 관리로 초기화된다.

### 전역 새로고침

앱 최상위에는 숫자형 새로고침 버전값이 있다.

- `_inquiryRefreshVersion`
- `_customerRefreshVersion`

푸시를 받거나 전역 갱신이 필요할 때 버전값을 올리고, 각 목록 화면은 `didUpdateWidget`에서 변화를 감지해 API를 다시 호출한다.

문의 목록은 추가로 다음 시점에 갱신된다.

- 화면 최초 진입
- 당겨서 새로고침
- 앱이 백그라운드에서 다시 활성화될 때
- 문의 상세에서 목록으로 돌아올 때
- 상태·배정 변경 후
- FCM 수신 후

현재 주기적인 타이머 폴링은 없다.

## 5. 관리자 역할과 권한

관리자 계정은 `AdminUser` 한 모델을 사용하며 두 불리언으로 권한을 구분한다.

- `isSuperAdmin`: 최고 관리자
- `isAssistantAdmin`: 보조 관리자
- 둘 다 아니면 일반 관리자

앱 모델의 편의 권한:

- `canManageInquiries`: 최고 관리자 또는 보조 관리자
- `canManageWebsite`: 최고 관리자 또는 보조 관리자

### 권한표

| 기능 | 최고 관리자 | 보조 관리자 | 일반 관리자 |
|---|---:|---:|---:|
| 전체 문의 조회 | 가능 | 가능 | 불가 |
| 내 문의 조회 | 가능 | 가능 | 가능 |
| 문의 담당자 배정·해제 | 가능 | 가능 | 불가 |
| 본인 외 담당 문의 완료 | 가능 | 가능 | 불가 |
| 본인 담당 문의 완료 | 가능 | 가능 | 가능 |
| 전체 고객 조회 | 가능 | 가능 | 불가 |
| 본인 담당 문의의 고객 조회 | 가능 | 가능 | 가능 |
| 고객 즐겨찾기·메모 | 가능 | 가능 | 접근 가능한 고객만 가능 |
| 중복 검토 목록 탭 | 가능 | 불가 | 불가 |
| 고객 상세 병합 UI | 가능 | 불가 | 불가 |
| 병합 기록·되돌리기 | 가능 | 불가 | 불가 |
| 고객 연결 해제 | 가능 | 불가 | 불가 |
| 홈페이지 관리 | 가능 | 가능 | 불가 |
| 관리자 추가·수정·삭제 | 가능 | 불가 | 불가 |
| 보조 관리자 임명·해제 | 가능 | 불가 | 불가 |
| 문의 처리·배정 로그 | 가능 | 불가 | 불가 |

### 중복 고객 처리 권한

- 최고 관리자만 중복 후보의 상세 비교와 최종 합치기·연결·새 고객 유지·복구를 수행한다.
- 보조 관리자와 일반 관리자는 접근 가능한 문의·고객에서 중복 감지 여부를 확인하고 최고 관리자에게 검토를 요청할 수 있다.
- 서버 API도 같은 기준으로 최종 처리 권한을 다시 확인한다.

### 관리자 표시 이름 원칙

- 앱에서 문의 담당자를 표시할 때는 사용자 ID가 아니라 표시 이름만 보여준다.
- 표시 이름이 없으면 `표시 이름 없음`을 사용한다.
- 관리자 목록에서는 계정 식별과 관리를 위해 로그인 ID도 별도로 표시한다.
- 문의 배정 후보에는 표시 이름과 역할을 보여주되, 일반 문의 화면에는 로그인 ID를 노출하지 않는다.

## 6. 전역 내비게이션

### 하단 내비게이션

왼쪽부터 다음 순서다.

1. `문의 관리`
2. `고객 관리`

두 항목 모두 아이콘과 텍스트 라벨을 함께 사용한다.

### 문의 화면 햄버거 메뉴

권한이 없는 항목은 빈 자리 없이 숨긴다. 상단부터 다음 구조다.

```text
관리자 프로필
├─ 표시 이름
├─ 로그인 ID
└─ 역할

메뉴
├─ 관리자     ← 최고 관리자만
├─ 홈페이지   ← 최고 관리자/보조 관리자만
├─ 처리 기록  ← 최고 관리자만
└─ 설정       ← 모든 관리자

로그아웃       ← 하단
```

각 메뉴는 아이콘과 이름을 함께 표시하며 로그아웃은 실행 전 확인한다.

## 7. 로그인 화면

파일: `admin_app/lib/screens/login_screen.dart`

### 화면 구성

- 상단 웹 로고
- 제목: `아델슨 관리자 앱`
- 안내: `관리자 계정으로 로그인해 홈페이지 문의를 확인하세요.`
- 관리자 ID 입력
- 비밀번호 입력
- 비밀번호 표시/숨김
- 로그인 버튼
- 실패 시 오류 문구

폼 폭은 큰 화면에서도 지나치게 넓어지지 않도록 제한한다.

### 인증 동작

1. `POST /api/admin/login`
2. 성공 응답의 JWT를 `flutter_secure_storage`에 `admin_token` 키로 저장
3. `ApiClient`의 Bearer 토큰으로 설정
4. `/api/admin/me`로 사용자 정보 재확인
5. FCM 기기 토큰 등록
6. 문의 관리 화면으로 이동

### 중복 감지와 기존 고객 연결

중복 후보가 있을 때 상세 하단에 `기존 고객 가능성` 카드가 표시된다.

중복 판단 근거:

- 같은 전화번호
- 같은 이메일
- 같은 회사명
- 이름만 같은 경우는 중복으로 보지 않음

후보 카드에는 다음이 있다.

- 감지 이유
- 후보 고객명과 회사명
- 후보 고객의 이전 문의 수
- 펼쳐볼 수 있는 이전 문의 접수번호
- 이전 문의로 이동
- `이 후보 1명 연결`
- `새 고객으로 유지`

연결 방식:

1. 기준은 현재 문의가 자동 생성한 신규 고객이다.
2. 후보 하나를 선택한다.
3. 확인 대화상자를 거친다.
4. 선택한 한 고객에만 연결한다.
5. 다른 후보는 계속 검토 대상으로 남는다.

자동 병합하지 않는 이유는 같은 회사의 다른 담당자일 수 있기 때문이다.

중복 후보가 없고 연결된 고객이 있으면 최고 관리자에게 연결 고객 정보와 `연결 해제` 동작을 보여준다.

- 일반 관리자는 본인 담당 문의만 완료할 수 있다.
- 완료 버튼을 누르면 확인 대화상자를 거친다.
- `PENDING`에서 `COMPLETED`로 실제 변경될 때 완료 로그가 생성된다.

- 해당 병합으로 이동된 문의들이 아직 대상 고객에 있는지

## 13. 고객 자동 생성과 중복 판정

### 문의 접수 시

공개 웹 문의폼이 제출되면 다음 데이터를 기준으로 문의와 고객을 만든다.

- 전화번호
- 이름
- 회사명
- 이메일
- 문의 내용
- 첨부파일

관리자가 모든 고객을 직접 등록하는 구조가 아니다.

### 중복 후보 규칙

| 일치 항목 | 처리 |
|---|---|
| 전화번호 동일 | 기존 고객 후보 |
| 이메일 동일 | 기존 고객 후보 |
| 회사명 동일 | 같은 회사의 다른 담당자일 수 있는 후보 |
| 이름만 동일 | 중복으로 판단하지 않음 |

후보가 있으면 `CustomerDuplicateReview`를 `PENDING` 상태로 만들고 자동 병합은 하지 않는다.

### 고객 병합

병합 시:

1. 기준 고객은 유지한다.
2. 선택한 원본 고객의 문의를 기준 고객으로 이동한다.
3. 원본 고객을 보관 상태로 전환하고 `mergedInto`를 기록한다.
4. 중복 검토 관계를 정리한다.
5. 즐겨찾기 관계를 가능한 범위에서 이전한다.
6. `CustomerMergeLog`를 만든다.
7. 실제 이동한 문의를 `CustomerMergeInquiry`에 개별 기록한다.
8. 선택하지 않은 다른 후보는 계속 남긴다.

### 새 고객으로 유지

후보가 실제 동일 고객이 아니면 `새 고객으로 유지`를 선택한다. 해당 중복 검토는 별도 고객으로 유지한 것으로 해결 처리된다.

### 연결 해제

최고 관리자는 잘못 연결된 문의를 고객에서 분리할 수 있다. 서버는 문의를 위한 별도 고객 관계를 만들고 중복 검토 상태를 별도 유지로 정리한다.

## 18. 인증과 세션

### JWT

- 로그인 API가 관리자 ID와 비밀번호를 검증한다.
- 비밀번호는 bcrypt 해시로 비교한다.
- JWT에는 관리자 ID와 사용자명이 포함된다.
- 기본 만료 설정은 `3650d`, 약 10년이다.
- 자동 연장 방식의 세션은 아니다.

### 매 요청 검증

서버는 Bearer JWT 서명만 확인하는 데서 끝나지 않고 DB에서 현재 관리자 계정을 다시 읽는다.

- 계정이 삭제됨
- 계정이 비활성화됨
- 토큰이 잘못됨

이 경우 요청을 거부한다.

### 앱 저장

- 토큰 키: `admin_token`
- 저장 위치: 플랫폼 보안 저장소
- 앱 재실행 시 `/api/admin/me`가 실패하면 토큰을 지우고 로그인 화면으로 보낸다.

### 운영상 주의

10년 만료 토큰은 로그인 풀림을 줄이는 대신 유출 시 유효기간이 매우 길다. 강제 로그아웃, 기기별 세션 철회, 짧은 액세스 토큰과 갱신 토큰 구조가 필요하면 현재 인증 설계를 별도로 변경해야 한다.

## 19. API 통신 공통 규칙

파일: `admin_app/lib/services/api_client.dart`

- 모든 관리자 요청에 `Authorization: Bearer <token>`을 붙인다.
- JSON 요청은 `GET`, `POST`, `PATCH`, `PUT`, `DELETE`를 지원한다.
- 일반 요청 제한시간: 30초
- 대용량 파일·서명 URL 업로드 제한시간: 5분
- 응답의 `success`가 참이 아니거나 HTTP 상태가 실패면 예외로 처리한다.
- 네트워크, 시간초과, 서버 오류, 파일 업로드 오류를 한국어 사용자 메시지로 변환한다.

## 22. 핵심 업무 흐름

### 신규 문의에서 완료까지

```text
웹 문의 제출
→ 문의·고객 자동 생성
→ 기존 고객 후보 탐색
→ 최고 관리자에게 신규 문의 알림
→ 전체 문의 > 배정 전
→ 최고/보조 관리자가 담당자 선택
→ 확인 버튼과 대화상자
→ 담당자 저장 + 배정 로그
→ 담당자에게 푸시
→ 담당자의 내 문의 > 진행 중
→ 고객 연락·문의 처리·메모
→ 처리 완료 확인
→ 완료 로그
→ 내 문의 > 처리 완료
```

### 중복 고객 처리

```text
문의 접수
→ 전화/이메일/회사명 비교
→ 후보가 있으면 중복 감지
→ 자동 병합하지 않음
→ 문의 상세 또는 고객 상세에서 후보 확인
├─ 기존 고객으로 연결/병합
│  ├─ 선택한 후보 한 건만 처리
│  ├─ 다른 후보는 계속 유지
│  └─ 병합 기록 생성
└─ 새 고객으로 유지

잘못 병합한 경우
→ 고객 상세 > 병합 기록
→ 해당 기록 한 건 선택
→ 안전 조건 확인
→ 한 건만 되돌리기
```


## 23. 오류·빈 상태·안전장치

### 목록

- 로딩: 중앙 로딩 표시

- 검색 결과 없음: 검색 기준이 포함된 빈 상태 문구
- 필터 결과 없음: 배정 전, 진행 중, 완료 상태별 빈 문구

## 27. 수정 시 반드시 지켜야 할 현재 불변식

1. 관리 권한자의 기본 문의 범위는 `전체 문의`다.
2. `전체 문의`는 `내 문의`보다 왼쪽에 있다.
3. 배정 전은 `PENDING + 담당자 없음`이다.
4. 전체 문의의 진행 중은 배정된 `PENDING` 문의다.
5. 담당자 드롭다운 선택만으로 바로 배정하지 않는다.
6. 일반 관리자는 본인에게 배정된 문의만 관리한다.
7. 신규 문의 알림은 최고 관리자에게만 간다.
8. 담당자는 본인이 배정받을 때만 배정 알림을 받는다.
9. 홈페이지 관리는 최고 관리자와 보조 관리자만 사용한다.
10. 관리자 관리와 활동 로그는 최고 관리자만 사용한다.
11. 중복 고객은 자동 병합하지 않는다.
12. 이름만 같은 고객은 중복 후보로 만들지 않는다.
13. 후보 하나를 병합해도 선택하지 않은 다른 후보는 남아야 한다.
14. 병합은 기록 한 건 단위로 되돌릴 수 있어야 한다.
15. 문의 카드의 회사명은 값이 없으면 빈 공간도 만들지 않는다.
16. 문의 담당자는 일반 문의 화면에서 표시 이름만 보여준다.
17. 이메일이 있으면 문의 상세에서 복사 동작을 제공한다.
18. 최고 관리자에게만 문의 카드와 상세 앱바의 `중복 감지` 라벨을 보여준다.
19. 최고 관리자에게만 관리자 메모 아래 `이전 문의 N건`을 보여준다.
20. CMS 저장 시 수정하지 않은 기존 자산까지 전체 목록에 유지한다.

## 29. 다른 AI가 기능을 변경할 때의 확인 순서

3. Flutter 모델이 서버 응답 필드를 실제로 파싱하는지 확인한다.
